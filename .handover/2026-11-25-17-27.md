## 5. 設計判断の記録
- **判断（Ryota・11/25）**: 指導者にも、本人の招待を出す。
  - **入れ方**: 本人（client）の招待は owner と coach。指導者（coach）の招待と、人を外す操作は owner だけ。coach が見られる・取り消せる招待は、自分が作ったものだけ。同じ人あてに作り直すと、前のコード（ほかの人が作ったものも）は無効になる。
  - **含み**: 指導者は、アカウントがまだ結びついていない人なら、誰でも招ける（管理者自身の記録の人も選択肢に出る）。管理者・指導者の `member_id`（自分は誰か）は、いまは空のまま。
  - **却下案**: 指導者に参加者の一覧（メールアドレスつき）を見せる案。結びつき済みの人の ID だけを返す関数にした。
- **判断（Ryota・11/25）**: 本人がグループを抜けるとき、記録を残すか消すかを本人に選ばせる。
  - **入れ方**: 「消す」は、行を残したまま中身を空にして「削除済み」にする。行そのものを消すと、ほかの端末に削除が届かず、古い写しが残って、つなぎ直したときに戻ってきてしまう。消えるのは本人の記録（6つのコレクション）。人（members）の行は残る。本人の端末の記録は、どちらを選んでも残る。何も指定しないと「残す」。
  - **入れ方**: 「残して抜ける」は、まだ送っていない記録を先に送ってから抜ける。
  - **入れ方**: 消して抜けた本人が招待コードで入り直すと、端末に残っている記録を預け直す（サーバーの削除済みを、端末の記録で上書きする）。別の端末でのつなぎ直しでは、いままでどおりサーバーの削除が勝つ。
  - **範囲外**: 管理者が本人を外したときは、記録は残る（本人は選べない）。指導者が抜けるときは、どちらを選んでも記録は変わらない。
- **判断**: 受け取りの続きは、(更新時刻, コレクション, ID) の3つで決める（`pull_records`。呼んだ人の権限で読む）。
  - **理由**: 更新時刻だけだと、同じ時刻の記録（1回の送信は最大500件、まとめての削除は全件）が1000件の境目にあるとき、残りを取りこぼす。
  - **却下案**: トリガーの時刻を1行ごとに変える案（同じ時刻にならない保証がない）。アプリ側で条件を組む案（ID に記号が入ると壊れやすい）。
- **判断**: 権限は `records.member_id` で判定し、その値はトリガー（`touch_record`）が `data` から決める。送られてきた `member_id` は使わない。
  - **理由**: 送る側が自分で持ち主を名乗れると、本人が他人の記録を自分のものにできる。
  - **却下案**: アプリが `member_id` 列を送る案。
- **判断**: 本人（client）が書けるのは、自分の記録（6つのコレクション）だけ。人（members）と profile は書けない。
  - **理由**: 本人が自分の members 行を消すと、指導者の画面からその人が消える。
  - **却下案**: 本人に自分の名前の変更を許す案。
- **判断**: 参加・招待・外す・抜ける・一覧・受け取りは、関数（RPC）を通す。`authenticated` が表を直接さわれるのは、`records`（読む・足す・直す）と `workspaces`（読む・名前の変更）だけ。`anon` には何も渡さない。
  - **理由**: 役割の書き換えや自分を参加者に足す経路を、表の権限ごとなくすため。
  - **却下案**: `workspace_members` と `invites` を RLS だけで守って直接読ませる案。
- **判断**: 招待コードは10文字（0・1・I・O を除く32種）、1回きり、既定で7日（最長30日）。データベースにはハッシュだけを持つ。参加する前に、招待の中身（グループ名・役割・誰の記録か）を見せる（`invite_info`）。
  - **理由**: コードを知っている人は記録に届く。参加した時点で、その端末の記録が送られる。
  - **却下案**: コードをそのまま保存して何度でも表示する案。コードを入れたらすぐ参加する案。
- **判断**: 端末をグループにつなぐときは、サーバーにまだない記録だけを送る。同期のたびに自分の役割を確かめ、グループから外れていたら、その端末の同期を止める（端末の記録は残す）。
  - **理由**: 古い内容での上書きと、送れない記録がたまり続けるのを防ぐため。
  - **却下案**: つなぐたびに全部を送り直す案。
- **判断（Ryota・11/25）**: 外された指導者の端末に残る記録は、残る側が選ぶ。
  - **入れ方**: 管理者が指導者を外すときに、その場で「残して外す／消して外す」を選ぶ（`remove_member` の `wipe_device`。何も指定しなければ残す）。選んだ内容は `departures` に置き、外された人の端末だけが `my_departure` で読める。入り直すと消える。
  - **入れ方**: 相手の端末は、同期しようとして「もう入っていない」と分かったときに `my_departure` を読む。消す指示なら、その端末がグループにつなぐ前から持っていた人（`localStorage` の `physlog.brought` に控える。同期を止めても・外れても消さない）と、その人の記録だけを残し、ほかを端末から消す（profile は空に戻す。写真の画像も消す）。指示を読めなかったとき（通信の失敗）は、何も消さず、つないだままにして次の同期でやり直す。
  - **範囲外**: 指導者が自分から抜けたときは、選ぶ場面がないので、端末の記録は残る。本人（client）を外すときは、相手の端末は変えない（本人の端末にあるのは本人の記録だけ）。あとから「やっぱり消す」に変える操作はない。
  - **含み**: 「持ち込んだ人」は、つないだときにサーバーにいなかった人。名前が同じでサーバーの人とまとめられた人は、持ち込んだ人に数えない（その人の記録はグループにあるので、消しても失われない）。指導者がつないだ後に足した人も、グループの人として消える。
  - **限界**: 相手の端末に電波がないあいだは消えない。アプリを開かなければ消えない。先に書き出したバックアップや画面の写しまでは消せない。協力的な端末での片づけであって、相手を信用しない前提の守りではない。

最優先は「4」の1です。Ryota がそのチャットで「適用して」と言ったら、`web/supabase/migrations/20261124150000_roles_and_invites.sql` を Supabase の physlog プロジェクトに適用し、`web/supabase/tests/roles_test.sql` を本番で流して `ROLLBACK_OK pass=248 fail=0` を確かめ、advisors を見ます。まだなら、適用はせずに、「4」の7（テキスト取り込みの記録ルール）を進めます。SQL やアプリを変えたら、`web/supabase/tests/run_local.sh` と `node web/tests/sync-roles.test.mjs`（手元の Postgres）、`npx tsc --noEmit -p .`、`npm run build:single` を通してから push します。

やらないこと：`main` へのマージ、GitHub Pages への公開、履歴の書き換えと強制 push、既存のプレビュー artifact への上書き公開、Supabase のデータやテーブルの削除、安全判定で止まった操作の回避。判断が要るところ（写真の置き場、履歴から記録を消すか、2人の記録を移すタイミング、管理者が外したときに本人の記録をどうするか、指導者が自分から抜けたときの端末の記録）は進めずに、作業ログに「判断待ち」として書いてください。終わったら `.handover/` に新しい引き継ぎを書き、作業ログに1行足します。
